# ADR-0011: Cron jobs scheduled by xcp-agent, run as transient units in the account's slice

- Status: accepted
- Date: 2026-11-02
- Amends: 01-architecture.md (`CronApply`), 06-service-drivers.md §1 (cron in the slice)

## Context

USR-ADV-01 needs cron jobs per account: add, edit and delete with a
schedule helper, output by email or kept as a log, and the last run's
status. 07-security says user code runs as the user inside the account's
slice. Ubuntu's cron runs a user's crontab as the user but in
`cron.service`'s cgroup, outside the slice and its limits, and tells nobody
how a job ended.

## Decision

- **The agent schedules.** `CronAccountApply` gives the agent all jobs of
  one account; it keeps them as a fragment (`/etc/xcp/cron/accounts/<user>.json`,
  root only, uid, gid and home found by the agent). Once a minute, at the
  minute, the agent starts each enabled job whose schedule matches, in the
  server's time zone (standard 5-field expressions, checked by
  `validate.CronSchedule`). Runs missed while the agent is down are skipped,
  as cron does.
- **Each run is a transient unit** started with `systemd-run --wait --pipe`:
  `xcp-cron-<user>-<job>.service`, as the account's user and group, in
  `xcp-u-<user>.slice`, from the home folder, with a minimal environment
  and at most 12 hours (no `NoNewPrivileges`: Postfix's `sendmail` needs its
  setgid `postdrop`, as under cron). The unit name keeps a job from
  overlapping itself: while a run is going, the next start is skipped and
  reported as such. At most 32 runs go at once on the server.
- **`xcp-cronrun`** is what the unit runs: as the account's user it starts
  `/bin/sh -c <command>` with stdin closed, passes the output on to the
  agent, and, when the job has an email address and printed something,
  mails the output with the server's `sendmail` as the user (like cron's
  `MAILTO`).
- **Last run:** the agent keeps each job's last start, duration, exit code
  and the last 16 KiB of output (`/var/lib/xcp-cron/<user>.json`, root only)
  and answers `CronStatus`. The panel shows it next to the job with the next
  run times.
- A suspended account's fragment has no jobs; suspension already stops its
  processes, running jobs included.

## Consequences

- Cron jobs count against the account's CPU, memory and task limits, and
  show up in `systemctl` and the journal under one name per job.
- No cron daemon is needed for accounts; the system's own cron keeps
  running for the system.
- Jobs are not jailed beyond running as the user; the jail is P3.
